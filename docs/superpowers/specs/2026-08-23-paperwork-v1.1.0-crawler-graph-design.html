2 · Tier A trap-to-escape rubric

All 20 hand-written traps. A trap with no documented escape measures nothing.

Plus one non-route trap: the Requests filter becomes a bottom-sheet Modal — overlay state, not a route (shown as the dotted “Filter sheet” ghost node above). LegalTerms is a real route rather than a Modal so it composes with the router and cannot collide with the cancel-confirm modal — two simultaneous Modals break on iOS.

3 · Tier A measures intelligence, Tier B measures scale

Two kinds of “more screens” — must not be collapsed into one number.

Tier A · adversarial

20 routes
  • Hand-written and heterogeneous — every route is a different trap shape.
  • Measures crawler intelligence: gates, aliasing, precondition edges, dead ends, cycles, destructive resets, format validation.
  • Scored per-trap against the documented escape in the rubric above.
  • A crawler that solves one Tier A trap tells you nothing about the next one.

Tier B · bulk

22 routes
  • Generated from a data registry through 4 generic renderers — ListScreen, DetailScreen, FormScreen, WizardScreen.
  • Structurally uniform across 5 clusters: Notifications, Insurance, Providers, Reminders, Security & data.
  • Measures scale: coverage-per-step and frontier prioritization under a bounded budget.
  • A crawler that solves one bulk cluster solves all of them — except the Inbox deep-links, the highest-value edges in this tier, which turn the tree into a graph.
Report two numbers, never one. Reporting Tier A and Tier B as a single blended coverage percentage would hide which one failed — a crawler can ace bulk-cluster coverage while missing every adversarial trap, or vice versa.

4 · P0 fixes to existing code

Pre-existing hardening gaps that block the eval — fix before adding new routes.
1

Android hardware back is unhandled most severe

With no navigation library, hardwareBackPress exits the app from any depth. A crawler tapping system back once would record “app crashed” instead of “went back one screen,” invalidating a large share of runs. Fix: a BackHandler effect in App.js that calls nav.back() when stack.length > 1 and the route is not a deliberate dead end, else returns false.

2

Modals swallow Android back

The existing cancel-confirm modal has no onRequestClose, so the agent is stuck with only the two on-screen buttons. Add it. Where a trap swallows back deliberately, comment that it is deliberate.

3

Unguarded param lookups

ServiceDetailScreen and BookingFormScreen call SERVICES.find(...) then dereference without a guard. Param-aliased routes plus a crawler re-pushing a stale id after the destructive reset makes undefined.title reachable. Add one shared <NotFound label nav /> to src/ui.js and guard every lookup screen — the ROUTES fallback only catches bad route names, not bad params.

4

{value && <Text/>} with numeric / empty-string values

Today's file is accidentally safe. New screens carry balances, item counts, and page counts, where balance: 0 renders a bare 0 outside <Text> and hard-crashes. All new conditionals use ?: or !!.

5

setTimeout cleanup

The slow-loading screen returns () => clearTimeout(t). Because screens remount per push, screen-local ready state replays the delay on every visit — intended behavior, chosen deliberately rather than discovered.
